Most agent risk comes from tool use, not text generation. Xenovia sees the tools an agent declares and the calls a model makes, and lets you govern them with policy.

## How tool calls appear in traces

### Tool definitions and model tool calls (agent endpoint)

When your app sends a `chat/completions` or `responses` request, the tool **definitions** you pass are visible to policy as `input.tools` and `input.tool_names`, and are recorded on the trace. When the model decides to call a tool, the **tool calls** it returns are captured on the turn as `output.tool_calls` (name, arguments, and call ID).

In the common pattern, your own code executes the tool and sends the result back as a `tool`-role message on the next request. That result is visible to the next request's policy as `input.tool_results` and is recorded on that turn. Client-executed tools are not separate child runs — they live in the turn's messages and output.

### MCP tools executed by the runtime

When a tool is executed through the Model Context Protocol by the runtime itself, Xenovia records it as its own child run with the tool name, arguments, result, status, and latency, alongside the model runs.

## Governing tools with policy

Tool governance is ordinary policy. The request-stage Rego sees the declared tools before the model is called, so a matching rule returns `403` before any tokens are spent. Read [Policies and Enforcement](/platform/policies-and-approvals) first for the decision contract.

<Note>
  `input.tool_names` lists the declared tool names exactly as your app sent them; comparisons are case-sensitive. `input.tools` carries the full schemas as `input.tools[_].name`, `.description`, and `.parameters_schema`; the keys of every tool object are lowercase. Use `tool_names` for allow/deny lists.
</Note>

### Block a tool by name

```rego
package xenovia
import future.keywords.if
import future.keywords.in

default decision = {"action": "allow"}

decision = {"action": "block", "rule": "no-db-writes"} if {
    some tool in input.tool_names
    startswith(tool, "db_write_")
}
```

### Allow only known-safe tools

```rego
package xenovia
import future.keywords.if
import future.keywords.in

default decision = {"action": "allow"}

safe := {"db_read", "get_user_profile", "list_records"}

decision = {"action": "block", "rule": "tool-allowlist"} if {
    some tool in input.tool_names
    not safe[tool]
}
```

### Escalate a destructive tool for human attention

```rego
package xenovia
import future.keywords.if
import future.keywords.in

default decision = {"action": "allow"}

decision = {"action": "escalate", "rule": "destructive-tool-review"} if {
    some tool in input.tool_names
    tool == "delete_account"
}
```

## Roles

The caller names its role with the `x-xenovia-agent-role` header on the agent endpoint, or with `agent_role` in the [Python SDK](/integrations/xenovia-sdk#roles-and-subagents). A role is verified only when the agent key lists it in its **allowed roles**; a role the key does not list is rejected with `403` `role_not_permitted`. On a key without allowed roles the role is unverified, and its guardrails only add to the agent's base guardrails.

## Recommended controls

- **Least privilege.** Blocklist high-risk tools explicitly rather than trusting a broad allowlist.
- **Separate by environment.** Use different agents, or different policies on one agent, for `dev`, `staging`, and `prod`. Never share production credentials.
- **Escalate irreversible actions.** Use `escalate` for deletions, financial writes, and cross-system state changes so they surface in Sessions and Alerts.
- **Review from evidence.** Traces show which tools are actually called. Remove rules for tools that no longer appear.

## Starting from a template

Several shipped policy templates cover tool access directly — for example an approved-tool allowlist, tool-argument PII blocking, and tool-argument size caps. Instantiate one from the dashboard or the [management API](/api-reference/introduction) rather than writing Rego from scratch.

## Governing actions outside the model call

Tool governance here covers tools the model requests through the agent endpoint. To gate actions your code takes on its own — tool calls and results, memory writes, database writes, outbound API calls — use the [Xenovia Python SDK](/integrations/xenovia-sdk).
