Xenovia Runtime is a high-performance Go service that speaks the OpenAI wire format. It exposes two routes per agent, plus the [Python SDK](/integrations/xenovia-sdk)'s decision endpoint `POST /v1/execute`, and passes every request through a fixed pipeline before and after the upstream model call.

## Request flow

Before any plugin runs, the router prepares the request: it validates the agent ID, checks the path, method, and content modality, sets the internal `X-Xenovia-Agent-Path`, authenticates the key against the agent in the URL, and only then resolves the agent's provider — rewriting the request's `model` to the agent's configured provider and model. Then the plugin pipeline runs.

```
Request
  │  router: validate agent ID · check path/method/modality · authenticate key · resolve provider + rewrite model
  ▼
  1. Auth        bind the agent identity (Redis, 5-min cache) and the verified role
  2. Session     resolve or create the session UUID, set the turn number
  3. Trace       open the turn record, stamp session/trace response headers
  4. Billing     check the organization's request allowance
  5. Policy      evaluate the request-stage Rego (OPA, 200 ms eval timeout)
  6. Guardrails  evaluate the agent's model_request guardrails
  │
  ▼  Upstream model (OpenAI / Anthropic / Gemini / Azure / Bedrock / Groq / vLLM)
  │
  post-hooks: response-stage policy · model_response and tool_call guardrails · trace persist · session chain
  ▼
Response
```

<Note>
  Path, method, and body validation happen before authentication, so an unauthenticated caller can receive a `400`, `404`, or `405`. Every key that cannot act as the agent in the URL — unknown, revoked, another agent's, or a key for a draft or deleted agent — gets the same `401` `invalid api key for this agent`. A provider misconfiguration (`502`) is reported only to an authenticated caller.
</Note>

A session middleware wraps the whole router and stamps `X-Xenovia-Session-Id` and `X-Xenovia-Trace-Id` into the response headers before the first body byte, so streaming responses still carry them.

## Plugin details

### 1. Auth

- Accepts `x-xenovia-key: xe_...` or `Authorization: Bearer xe_...`.
- Resolves the key against Redis (`apikey:{sha256(key)}`, 5-minute TTL). On a miss it calls the control plane; a resolved identity is an HMAC-signed blob holding `agent_id`, `org_id`, and the key's `allowed_roles`.
- The key's agent must match the agent ID in the URL, unless the request carries a workflow header for same-organization cross-agent delegation.
- A role sent in `x-xenovia-agent-role` is verified when the key's `allowed_roles` list it; an unlisted role is rejected with `403` `role_not_permitted`.
- Organization keys (`ak_...`) are rejected here — they authenticate the [management API](/api-reference/authentication), not the runtime.
- Keys are never logged; only an 8-character SHA-256 prefix appears in logs.

### 2. Session

Five strategies, first match wins:

| Priority | Source | Mechanism |
|----------|--------|-----------|
| 1 | `X-Xenovia-Session-Id` header | Must be a UUID; a malformed value is rejected with `400` |
| 2 | `previous_response_id` (Responses API) | Looked up per API key |
| 3 | `user` field (Chat Completions) | Looked up per API key; the value is stored only as a SHA-256 hash |
| 4 | Message fingerprint | Hash of the messages up to the last assistant turn |
| 5 | New session | A fresh UUID |

Turn numbers increment per session (30-minute sliding TTL). Sessions are isolated per API key for strategies 2–4, and cross-organization reuse of an explicit session ID is rejected.

### 3. Trace

- Opens a turn record and emits child runs: the model call, plus policy, escalation, and runtime-executed tool runs.
- Custom `X-Xenovia-Property-*` headers are attached to the turn (see [Traces and Remediation](/platform/traces-and-remediation)).
- Persistence is asynchronous. Under sustained overload a record can be dropped rather than block the request.

### 4. Billing

There is no per-agent rate limit. The runtime checks the organization's request allowance and returns `402` when it is exhausted or billing access is restricted.

### 5. Policy

Evaluates the request-stage Rego against the full request context, then the response-stage Rego after the model replies. See [Policies and Enforcement](/platform/policies-and-approvals) for the decision contract and the input schema. Policies are cached per agent and revalidated about every five minutes.

### 6. Guardrails

The intent check and its triggers are gone; the agent's [guardrails](/platform/policies-and-approvals#guardrails) run instead, evaluated by Xenovia's guardrail service: `model_request` guardrails after the request-stage policies, then `model_response` guardrails and a `tool_call` guardrail per proposed tool call after the model replies. `tool_result`, `memory_write`, and `context_summary` guardrails run only through the SDK.

- A guardrail `escalate` lets the request proceed; a `block` returns `403`.
- The block or escalation reason is recorded server-side and never returned to the caller.
- There is no fail mode setting: an enforced guardrail that cannot be evaluated fails closed with `503`, and a Monitor guardrail that fails records the error and never blocks.

## Supported providers

Xenovia speaks OpenAI format and translates to each provider upstream, so your app always uses an OpenAI-compatible client.

| Provider | Handling |
|----------|----------|
| OpenAI | Native |
| Anthropic, Google Gemini, Azure OpenAI, Amazon Bedrock | Translated from OpenAI format |
| Groq | OpenAI-compatible |
| vLLM and other OpenAI-compatible endpoints | Routed by base URL |

An OpenAI-typed provider configured with a base URL is routed as vLLM; one configured for Azure (an Azure endpoint or API version) is routed as Azure. The provider your policy sees in `input.provider` is this resolved value.

## Supported endpoints

| Endpoint | Use case |
|----------|----------|
| `POST /v1/chat/completions` | Chat, agents, tool calling |
| `POST /v1/responses` | OpenAI Agents SDK (Responses API) |

Embeddings, legacy completions, model listing, and audio, image, video, batch, and container endpoints are not routed and return `404`. Only these two inference routes and the health endpoints are served. Text, image, and file **inputs** are accepted on both routes; audio output and other modalities are rejected with `400`.

## Security

- **Credential isolation.** Provider credentials live in the agent's configuration and are resolved server-side; your app never holds them. Secrets are fetched over an internal channel and kept in memory, never written to Redis or into telemetry.
- **SSRF protection.** vLLM and Azure base URLs are validated; link-local and cloud-metadata addresses are rejected. Loopback and private vLLM addresses are rejected unless the runtime sets `XENOVIA_ALLOW_PRIVATE_PROVIDER_ENDPOINTS` (see [Hybrid deployments](#hybrid-deployments)).
- **Config integrity.** Config snapshots and identity blobs are HMAC-signed. A revoked agent key stops working within about five minutes in the cloud.
- **Deployment.** In the standard cloud deployment Xenovia operates the runtime. A hybrid data-plane option runs the runtime inside your own cluster; ask your Xenovia contact for the deployment guide.

## Hybrid deployments

A hybrid agent is served by the runtime in your own cluster. Its provider uses a credential reference that your cluster resolves at request time, and its endpoint is your deployment's ingress URL followed by `/{agent_id}/v1`.

These runtime settings govern guardrails and model routing in a hybrid deployment:

| Variable | Default | Meaning |
|----------|---------|---------|
| `GUARDRAIL_URL` | unset | Base URL of the guardrail service. Required for guardrails |
| `GUARDRAIL_SECRET` | unset | Shared secret sent to the guardrail service. At least 16 characters, and the same value the guardrail service uses |
| `XENOVIA_GUARDRAIL_CONCURRENCY` | `64` | Guardrail checks allowed at once per runtime process; further checks wait for a slot within their own deadline |
| `XENOVIA_ALLOW_PRIVATE_PROVIDER_ENDPOINTS` | `false` | `true` lets vLLM and OpenAI-compatible base URLs target loopback, private, CGNAT, and cluster-local addresses. For hybrid and local development only; link-local and cloud-metadata addresses stay blocked |

<Warning>
  Without `GUARDRAIL_URL`, every guardrail errors: enforced guardrails fail closed with `503`, and Monitor guardrails record an error. Policies do not depend on it.
</Warning>
