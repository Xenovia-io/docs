## Core concepts

<CardGroup cols={3}>
  <Card title="Agents" icon="hexagon-nodes">
    Operator-created entry points. An agent has an owner, a single provider, attached policies, and guardrails. All governance is scoped to an agent.
  </Card>
  <Card title="Providers" icon="plug">
    A provider holds the upstream credential and model for an agent. One provider per agent; credentials are resolved server-side.
  </Card>
  <Card title="Policies" icon="gavel">
    Rego rules evaluated by OPA. Request-stage decisions are `allow`, `block`, `redact`, or `escalate`; response-stage decisions are `allow`, `block_response`, `redact_response`, or `escalate`.
  </Card>
  <Card title="Sessions" icon="fingerprint">
    A session groups related turns. Xenovia resolves one for every request; you can also set it explicitly.
  </Card>
  <Card title="Guardrails" icon="brain">
    Named semantic checks, including the agent's **scope guardrail** for what it is for, across model, tool, memory, and summary stages. They can allow, block, redact, or escalate.
  </Card>
  <Card title="Traces" icon="file-waveform">
    The record of what happened: turns, model and tool runs, token counts, latency, decisions, and custom properties.
  </Card>
</CardGroup>

## Terminology

The platform nests telemetry three levels deep. The names differ slightly between screens, so this is the model to hold:

| Term | What it is |
|------|------------|
| **Session** | A group of related turns, resolved per request or set with `X-Xenovia-Session-Id`. The **Sessions** page lists these. |
| **Turn** | One request/response cycle through an agent, or one SDK check. A turn carries the policy decision, tokens, and latency. (Some screens call a turn a "trace".) |
| **Run / step** | A unit of work inside a turn — the model call, a policy check, a runtime-executed tool. |
| **Workflow** | Turns across several agents grouped by a shared workflow ID, for multi-agent runs. |
| **Guardrail** | A named semantic check. The **scope guardrail** describes what the agent is for. |
| **Escalation** | A step queued on its session for human review and resolved with a note. A policy escalation blocks with `403`; a guardrail escalation lets the call proceed. |

## How an agent is put together

```
Agent
 ├── Provider (one: OpenAI / Anthropic / Gemini / Azure / Bedrock / Groq / vLLM)
 ├── Request-stage policies (Rego)
 ├── Response-stage policies (Rego)
 ├── Guardrails (scope guardrail + named checks, optionally per role)
 ├── API keys (xe_…)
 └── Sessions
      └── Turns
           ├── Policy decision (action, rule)
           ├── Model and tool runs
           └── Custom properties (X-Xenovia-Property-*)
```

## Agent setup

A new agent starts as a **draft**. Setup has four steps — **Purpose** (including how it connects: **Agent endpoint**, **SDK only**, or **Hybrid deployment**), **Model route** (skipped for SDK-only agents), **Protection** (in Monitor, switched on at activation), and **Connect** — after which you **Activate** the agent and send its first request. The runtime rejects a draft agent's keys with `401`. See the [Quickstart](/getting-started/quickstart).

## Request lifecycle

<Steps>
  <Step title="Validate">
    The runtime validates the agent ID, the path, and the content.
  </Step>
  <Step title="Authenticate">
    The `xe_...` agent key is verified and must belong to the active agent in the URL.
  </Step>
  <Step title="Route">
    The agent's provider is resolved, replacing the request's model with the agent's configured model.
  </Step>
  <Step title="Resolve the session">
    A session and turn number are resolved, and `X-Xenovia-Session-Id` and `X-Xenovia-Trace-Id` are stamped into the response headers.
  </Step>
  <Step title="Enforce policy and guardrails">
    The request-stage Rego runs, then `model_request` guardrails. A `block` returns `403`; a `redact` strips fields; a policy `escalate` blocks and is queued for review.
  </Step>
  <Step title="Call the model and check the response">
    The upstream model is called, the response-stage Rego and `model_response` guardrails run, `tool_call` guardrails check any tool calls the model proposed, and the completed turn is persisted.
  </Step>
</Steps>

## Agent endpoint

Every agent exposes an OpenAI-compatible base URL:

```
https://runtime.xenovia.io/{agent_id}/v1
```

Only `/v1/chat/completions` and `/v1/responses` are served. Any other path under the agent — `/v1/embeddings`, `/v1/completions`, `/v1/models`, provider-prefixed paths such as `/openai/v1/...`, and the legacy `/a/{agent_id}/...` prefix — returns `404`. The Python SDK's decision endpoint is `POST https://runtime.xenovia.io/v1/execute`; the key identifies the agent.

## What the platform does not expose

- **Provider credentials** live in the agent's configuration, never in your app or in telemetry.
- **Raw API keys** are never logged; only a short SHA-256 prefix appears.
- **Block and escalation reasons** are recorded server-side and are never returned to the agent.
