Xenovia evaluates [Open Policy Agent (OPA)](https://www.openpolicyagent.org/) Rego policies on every request to an agent. Policies are created in the control plane, attached to an agent, and enabled. Each agent can run policies at two stages:

- **Request stage** — before the request is forwarded to the upstream model.
- **Response stage** — after the model responds, before the reply reaches your app.

Enabled policies are compiled to a per-agent snapshot, pushed to the runtime, and revalidated by each runtime instance about every five minutes. OPA evaluates with a 2-second compile timeout and a 200-millisecond per-stage evaluation timeout.

## The decision contract

A policy returns a single `decision` object. This is the only value the runtime reads — `allow`/`deny` rules or a bare `redact_fields` set are ignored.

```rego
package xenovia

import future.keywords.if
import future.keywords.in

# Allow by default; a matching rule below overrides it.
default decision = {"action": "allow"}

decision = {"action": "block", "rule": "no-delete-tools"} if {
    some tool in input.tool_names
    tool == "delete_database"
}
```

- Write `package xenovia`. The control plane strips your `package` line and re-packages the rule under a system namespace, so the package name you choose does not matter.
- `action` is required; `rule` is a short identifier recorded on the trace. Any other key (including `reason`) is ignored by the runtime.
- Multiple complete `decision` rules must have mutually exclusive conditions. If two can be true at once, OPA reports a conflict and the request fails closed. Guard each rule with distinct conditions (for example on `input.agent_role`).

<Note>
  The Rego is compiled with `opa check --strict` when you save it. Compilation errors are returned as `422` with the OPA diagnostics.
</Note>

## Actions

| Stage | `action` | HTTP result | Effect |
|-------|----------|-------------|--------|
| Request | `allow` | — | Forward to the model |
| Request | `block` | `403` | Terminate; record the trace |
| Request | `redact` | — | Remove the listed fields from messages and tool definitions, then forward |
| Request | `escalate` | `403` | Terminate and record an escalation signal (see [Escalations](#escalations)) |
| Response | `allow` | — | Return the reply |
| Response | `block_response` | `403` | Suppress the reply; record the trace |
| Response | `redact_response` | — | Remove the listed fields from the reply, then return it |
| Response | `escalate` | `403` | Suppress the reply and record an escalation |

When several enabled policies run at the same stage, the strongest action wins: `block` over `escalate` over `redact` over `allow` (and `block_response` over `redact_response` at the response stage). An unrecognised `action` ranks below `allow` and can never block.

### Redaction

Return the labels to strip in `redact_fields`:

```rego
package xenovia
import future.keywords.if
import future.keywords.in

default decision = {"action": "allow"}

decision = {
    "action": "redact",
    "rule": "mask-contact-details",
    "redact_fields": ["email", "phone"],
} if {
    some msg in input.messages
    contains(msg.content, "@")
}
```

Supported labels: `email`, `ssn`, `phone`, `creditcard` (Luhn-validated), `ip`, `url`. Redaction applies to message text, tool descriptions, and the Responses `instructions` field at the request stage, and to the reply text at the response stage. Streamed replies are buffered and checked before any content is sent, so response redaction applies to them too.

## Monitor vs enforce

Enforcement is a property of the policy, set in the dashboard (**Monitor** or **Enforced**) or through the API, not something you express in Rego:

- **Enforced** policies apply their action.
- **Monitor** policies are evaluated and their would-be decision is recorded on the trace, but the action is never applied. Use monitor mode to trial a policy against live traffic before enforcing it.

## Policy input

Both stages receive the same base fields; each stage adds its own.

### Base fields (both stages)

```json
{
  "agent_id":      "string — the agent's ID",
  "org_id":        "string — organization ID",
  "request_type":  "chat_completion | chat_completion_stream | responses | responses_stream",
  "provider":      "resolved upstream provider (openai, anthropic, gemini, azure, bedrock, groq, vllm)",
  "model":         "the model the runtime will call — the agent's configured model, not the value your client sent",
  "stream":        "boolean",
  "messages":      "[{ role, content, tool_call_id?, tool_call_ids? }] — text only",
  "tools":         "[{ name, description, parameters_schema }]",
  "tool_names":    "[]string — the declared tool names, exactly as sent, convenient for allow/deny lists",
  "system_prompt": "string — first system message, if any",
  "agent_role":    "string — present only when the x-xenovia-agent-role header is sent",
  "http_headers":  "object — request headers, with secret values redacted"
}
```

### Request stage adds

```json
{
  "request":             "object — the normalised request (parameters under request.params)",
  "request_flat":        "object — the same request flattened to dotted keys",
  "request_max_tokens":  "int — requested output cap, 0 if unset",
  "tool_results":        "[{ tool_call_id, name, content }] — Chat Completions only",
  "agent_tokens_today":  "int — running token count for this agent today",
  "session_tokens_used": "int — running token count for this session",
  "workflow_context":    "{ workflow_id, decisions: [{ agent_id, trace_id, policy_action, timestamp }] } — prior cross-agent decisions, only with a workflow header"
}
```

### Response stage adds

```json
{
  "stage":  "response",
  "output": {
    "content":    "string — the reply text",
    "tool_calls": "[{ id, name, arguments }]"
  },
  "usage":         "{ input_tokens, output_tokens, total_tokens }"
}
```

## Examples

### Block a tool

```rego
package xenovia
import future.keywords.if
import future.keywords.in

default decision = {"action": "allow"}

decision = {"action": "block", "rule": "no-destructive-tools"} if {
    some tool in input.tool_names
    startswith(tool, "delete_")
}
```

### Require the agent's model to be on an allowlist

```rego
package xenovia
import future.keywords.if
import future.keywords.in

default decision = {"action": "allow"}

approved := {"gpt-4o", "gpt-4o-mini", "claude-sonnet-4-20250514"}

decision = {"action": "block", "rule": "model-allowlist"} if {
    not approved[input.model]
}
```

`input.model` is the model configured on the agent, so this rule guards against an agent routed to an unapproved model rather than a client choosing one.

### Cap output tokens (request stage)

```rego
package xenovia
import future.keywords.if

default decision = {"action": "allow"}

decision = {"action": "block", "rule": "output-cap"} if {
    input.request_max_tokens > 2000
}
```

### Block a refusal in the reply (response stage)

```rego
package xenovia
import future.keywords.if

default decision = {"action": "allow"}

decision = {"action": "block_response", "rule": "no-refusal"} if {
    input.stage == "response"
    contains(input.output.content, "I cannot help")
}
```

## Templates

Instantiate a shipped template with its parameters instead of writing Rego. Agent setup offers the templates recommended for the agent and creates the chosen ones in Monitor.

Thirteen templates were removed because the runtime never produces the inputs they read, or because they always escalated: `pii-pattern-block`, `rapid-call-rate-block`, `repeat-denial-escalation`, `anomalous-tool-pattern-escalation`, `tenant-boundary-match`, `external-disclosure-consent-gate`, `block-shadow-model-fallback`, `low-confidence-escalation`, `high-risk-tool-human-approval`, `financial-threshold-escalation`, `eu-ai-act-fundamental-rights-review`, `destructive-tool-confirmation`, and `workflow-intent-aggregate-escalate`. Policies you already created from them are unchanged; review whether they can still fire.

## Guardrails

Guardrails replace the former intent check. A guardrail is a named check that Xenovia's guardrail model evaluates at one or more stages (`model_request`, `model_response`, `tool_call`, `tool_result`, `memory_write`, `context_summary`), with an action (`allow`, `block`, `redact`, or `escalate`) and, like a policy, Enabled and Monitor or Enforce. The agent's **scope guardrail** (kind `scope`) describes in plain language what the agent is for; requests outside it are flagged. A guardrail can be limited to one agent role. `tool_result`, `memory_write`, and `context_summary` guardrails run only when your code sends those stages with the [Python SDK](/integrations/xenovia-sdk).

## What a block looks like to your app

A blocked request returns `403`. The runtime uses the gateway error envelope:

```json
{
  "is_bifrost_error": false,
  "status_code": 403,
  "error": { "message": "request blocked by policy" },
  "extra_fields": {}
}
```

The OpenAI SDK raises this as `PermissionDeniedError`. The message is deliberately generic; the rule that fired is recorded on the trace, not returned to the caller. The `X-Xenovia-Trace-Id` response header identifies the trace.

## Escalations

`escalate` is for actions you want flagged for human attention. When a policy escalates:

1. The call is blocked with `403`: a request-stage escalation returns `request blocked by policy`, and a response-stage escalation suppresses the reply with `response blocked by policy`.
2. An escalation is recorded, carrying the agent and matched rule.
3. Any alert rule watching for escalations fires (see [Alerts](/platform/traces-and-remediation)).

A guardrail with action `escalate` records an escalation the same way but lets the request proceed.

<Warning>
  There is no approve/deny queue today. A policy escalation blocks the call and raises a signal; a guardrail escalation raises the signal and lets the call proceed. Neither pauses the request for an operator to release. Review escalations in Sessions and in Alerts, resolve them with a note, then adjust the policy or guardrail. Reasons are recorded server-side and are never returned to the agent.
</Warning>
