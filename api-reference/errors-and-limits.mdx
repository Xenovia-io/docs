Xenovia has two surfaces and they return errors in different shapes. Check which one you are calling.

## Management API errors (`cp.xenovia.io`)

The management API returns FastAPI's error shape — a JSON object with a `detail` field:

```json
{ "detail": "Agent not found" }
```

Validation errors (`422`) return `detail` as a list describing each invalid field:

```json
{
  "detail": [
    { "type": "string_type", "loc": ["body", "name"], "msg": "Input should be a valid string", "input": 42 }
  ]
}
```

Every response carries an `X-Request-ID` header. Send your own value to have it echoed and recorded in the audit log, or read the generated one and log it alongside failures.

### Management API status codes

<CardGroup cols={2}>
  <Card title="400 Bad Request" icon="circle-exclamation">
    A domain rule was violated — for example activating an agent with no API key, or enabling a policy that is not attached to an agent.
  </Card>
  <Card title="401 Unauthorized" icon="key">
    Missing, malformed, expired, or revoked credential — or an agent `xe_` key used against the management API.
  </Card>
  <Card title="403 Forbidden" icon="lock">
    Valid credential without access: a `read`-scoped key on a write, an org key on a human-only endpoint, or an `org_id` that does not match your key's organization. (A resource that belongs to another organization returns `404`, not `403`.)
  </Card>
  <Card title="404 Not Found" icon="magnifying-glass">
    The resource does not exist or belongs to another organization. Cross-organization reads return `404`, not `403`.
  </Card>
  <Card title="409 Conflict" icon="code-compare">
    A uniqueness constraint — a duplicate agent, provider, policy, or guardrail name, or the 20-key limit for organization keys.
  </Card>
  <Card title="422 Unprocessable" icon="list-check">
    Schema validation failed, or a policy's Rego did not compile. The `detail` list names the problem.
  </Card>
</CardGroup>

`500` is an unexpected failure (`{"detail": "Internal server error"}`); include the `X-Request-ID` when contacting support. `503` means a dependency (key verification, or the config write path) is briefly unavailable — retry with backoff.

## Runtime errors (`runtime.xenovia.io`)

The runtime returns the gateway error envelope:

```json
{
  "is_bifrost_error": false,
  "status_code": 403,
  "error": { "message": "request blocked by policy" },
  "extra_fields": {}
}
```

`is_bifrost_error` is `true` when the error came from the upstream provider (a timeout, say), in which case `extra_fields` names the provider, model, and request type. OpenAI-compatible SDKs raise these as their usual typed errors (`403` → `PermissionDeniedError`, `429` → `RateLimitError`, and so on).

Errors raised before the request reaches the pipeline — body validation, authentication, and provider resolution (the `502` below) — use a shorter body, `{ "error": { "message": "..." } }`. An invalid agent ID in the URL returns `404` with an empty body, and a completely unknown path returns `404` with the plain-text body `Not Found`. The SDK's `POST /v1/execute` returns its own decision body; see the [Python SDK](/integrations/xenovia-sdk).

### Runtime status codes

| Status | Meaning |
|--------|---------|
| `400` | Invalid or empty JSON body, an unsupported modality or content part, or a malformed `X-Xenovia-Session-Id` |
| `401` | Missing key, or a key that cannot act as this agent: unknown or revoked, another agent's key, or a key for a draft or deleted agent (`invalid api key for this agent`) |
| `402` | The organization's request allowance is exhausted, or billing access is restricted |
| `403` | Blocked by an enforced policy or guardrail, or escalated by a policy |
| `404` | Unknown agent ID or unsupported path (only `/v1/chat/completions` and `/v1/responses` are served under an agent, plus the SDK's `POST /v1/execute` at the runtime root) |
| `405` | Wrong method on a supported path |
| `502` | The agent has no provider, or an ambiguous or invalid provider configuration |
| `503` | A dependency (auth, policy, or an enforced guardrail) was briefly unavailable |

### Policy and guardrail blocks

A policy block, a guardrail block, and a policy escalation all return `403` with a generic message. A guardrail escalation does not block. The specific reason is recorded server-side and is never returned to the caller. The `X-Xenovia-Trace-Id` header on the response identifies the trace — look it up in the platform to see the policy or guardrail that fired.

## Rate limits

The **management API does not rate-limit** requests today.

The **runtime** has no per-agent rate limit. Requests are metered against the organization's request allowance; when it is exhausted the runtime returns `402`. Upstream provider rate limits pass through as the provider's error (for example `429`, with `is_bifrost_error: true`).

## Retry guidance

| Status | Retry? | Notes |
|--------|--------|-------|
| `429` | Yes | Upstream provider limit; back off with jitter |
| `500`, `502`, `503` | Yes | Transient; retry with backoff |
| `400`, `422` | No | Fix the request |
| `401` | No | Fix the credential, or activate the agent |
| `402` | No | Billing; contact your administrator |
| `403`, `404` | No | A policy or guardrail decision, or a scope or resource problem, not transient |

Retries are not idempotent on the management API — no idempotency-key header is supported, so a retried `POST` can create a second resource (or return `409` where names are unique). Log `X-Request-ID` and `X-Xenovia-Trace-Id` for every non-2xx response.
