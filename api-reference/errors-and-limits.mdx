Xenovia has two surfaces and they return errors in different shapes. Check which one you are calling.

## Management API errors (`cp.xenovia.io`)

The management API returns FastAPI's error shape — a JSON object with a `detail` field:

```json
{ "detail": "Proxy not found" }
```

Validation errors (`422`) return `detail` as a list describing each invalid field:

```json
{
  "detail": [
    { "type": "string_type", "loc": ["body", "name"], "msg": "Input should be a valid string", "input": 42 }
  ]
}
```

Every response carries an `X-Request-ID` header. Send your own value to have it echoed and recorded in the audit log, or read the generated one and log it alongside failures.

### Management API status codes

<CardGroup cols={2}>
  <Card title="400 Bad Request" icon="circle-exclamation">
    A domain rule was violated — for example activating a proxy with no API key, or enabling a policy that is not attached to an active proxy.
  </Card>
  <Card title="401 Unauthorized" icon="key">
    Missing, malformed, expired, or revoked credential — or a proxy `xe_` key used against the management API.
  </Card>
  <Card title="403 Forbidden" icon="lock">
    Valid credential without access: a `read`-scoped key on a write, an org key on a human-only endpoint, or a resource in another organization.
  </Card>
  <Card title="404 Not Found" icon="magnifying-glass">
    The resource does not exist or belongs to another organization. Cross-organization reads return `404`, not `403`.
  </Card>
  <Card title="409 Conflict" icon="code-compare">
    A uniqueness constraint — a duplicate proxy, provider, policy, or capability name, or the 20-key limit for organization keys.
  </Card>
  <Card title="422 Unprocessable" icon="list-check">
    Schema validation failed, or a policy's Rego did not compile. The `detail` list names the problem.
  </Card>
</CardGroup>

`500` is an unexpected failure (`{"detail": "Internal server error"}`); include the `X-Request-ID` when contacting support. `503` means a dependency (key verification, or the config write path) is briefly unavailable — retry with backoff.

## Runtime errors (`runtime.xenovia.io`)

The runtime returns the gateway error envelope:

```json
{
  "is_bifrost_error": false,
  "status_code": 403,
  "error": { "message": "request blocked by policy" },
  "extra_fields": {}
}
```

`is_bifrost_error` is `true` when the error came from the upstream provider (a timeout, say), in which case `extra_fields` names the provider, model, and request type. OpenAI-compatible SDKs raise these as their usual typed errors (`403` → `PermissionDeniedError`, `429` → `RateLimitError`, and so on).

Two paths do not use this envelope: an invalid proxy ID in the URL returns `404` with an empty body, and a completely unknown path returns `404` with the plain-text body `Not Found`.

### Runtime status codes

| Status | Meaning |
|--------|---------|
| `400` | Invalid or empty JSON body, or an unsupported modality or content part |
| `401` | Missing key, or a key that is not a valid proxy (`xe_`) key |
| `403` | Blocked or escalated by policy or the intent guardrail |
| `404` | Unknown proxy ID or unsupported path (only `/v1/chat/completions` and `/v1/responses` are served) |
| `405` | Wrong method on a supported path |
| `429` | The proxy's per-minute rate limit was exceeded |
| `502` | The proxy has no provider, or an ambiguous or invalid provider configuration |
| `503` | A dependency (auth, policy, or intent scoring in fail-closed mode) was briefly unavailable |

### Policy and intent blocks

A policy block, an intent block, and an escalation all return `403` with a generic message. The specific reason is recorded server-side and is never returned to the caller. The `X-Xenovia-Trace-Id` header on the response identifies the trace — look it up in the platform to see the rule that fired.

## Rate limits

The **management API does not rate-limit** requests today.

The **runtime** enforces a per-minute request limit only when one is set on the proxy (`rate_limit_rpm`). By default no limit is applied. When the limit is exceeded the runtime returns `429`:

```json
{
  "is_bifrost_error": false,
  "status_code": 429,
  "error": { "message": "rate limit exceeded: proxy is limited to 60 requests/minute" },
  "extra_fields": {}
}
```

There is no `Retry-After` header. Back off with exponential jitter and retry.

## Retry guidance

| Status | Retry? | Notes |
|--------|--------|-------|
| `429` | Yes | Back off with jitter |
| `500`, `502`, `503` | Yes | Transient; retry with backoff |
| `400`, `422` | No | Fix the request |
| `401` | No | Fix the credential |
| `403`, `404` | No | A policy decision or a scope or resource problem, not transient |

Retries are not idempotent on the management API — no idempotency-key header is supported, so a retried `POST` can create a second resource (or return `409` where names are unique). Log `X-Request-ID` and `X-Xenovia-Trace-Id` for every non-2xx response.
